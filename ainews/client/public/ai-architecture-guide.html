Architecture

先问模型在解决什么结构问题，再问它是否够大、够快、够稳。

同样是“AI 模型”，Transformer、CNN、LSTM、Mamba、Diffusion、MoE 解决的其实是完全不同的结构约束。 一个模型架构的价值，来自它如何处理上下文、局部模式、长期记忆、并行效率、生成质量和成本边界。

核心问题

序列如何建模

文本、语音、事件流，本质上都在处理“先后关系”和“远距离依赖”。

核心问题

局部如何提取

图像、视频、语音频谱依赖局部结构，CNN 仍然是强力基线。

核心问题

长上下文如何扩展

序列越长，注意力代价越高，所以状态空间与稀疏结构重新变得重要。

核心问题

质量与成本如何平衡

MoE、蒸馏、量化、推理框架，都是把“效果”翻译成“可部署成本”。

1. Transformer：当上下文关系比局部顺序更重要时，它仍是主架构。

Transformer 的根本突破不在“大”，而在于它把序列建模从“按时间一步步传”改成了“任意位置直接看任意位置”。 这使得语言模型、检索增强系统、多模态模型都能把远距离依赖直接编码进注意力矩阵里。

机制
自注意力 每个 token 生成 Query / Key / Value，核心是用相似度决定“看谁”，再把加权后的信息写回自身。
优点
并行训练、长依赖表达强 在训练时可以整段并行处理，不像 RNN 必须顺序滚动。
代价
注意力复杂度随序列平方增长 上下文越长，显存和延迟压力越大，长文本系统会被推理成本迅速放大。
适用
LLM、RAG、多模态理解、代码生成 几乎所有主流通用模型都建立在它的变体之上。
GPT: decoder-only BERT: encoder-only T5: encoder-decoder ViT: image patches

2. CNN：当你更在意局部模式、平移不变性和高效卷积时，不要把它过早判死刑。

CNN 最强的地方不是“老”，而是它天然适合图像、视频切片、医学影像、语音频谱这种局部结构稳定的信号。 它用卷积核扫描局部区域，本质上是在强行加入“邻近位置往往更相关”的先验。

  • 卷积层负责提取边缘、纹理、角点、形状等局部模式。
  • 池化层压缩空间分辨率，把“哪里有特征”转成“有没有这个特征”。
  • 深层网络把低级视觉模式逐层组合成物体部件和语义目标。
  • 在资源受限或视觉任务边界明确时，CNN 仍常常比 Transformer 更稳、更省。

什么时候优先考虑

  • 图像分类、检测、分割的中小规模场景
  • 对边缘设备推理成本非常敏感
  • 数据量有限，希望模型先验更强

什么时候不够

  • 跨区域依赖非常强的任务
  • 长程关系比局部纹理更重要
  • 需要统一承载文本、图像、音频的多模态建模

3. RNN / LSTM：它们不再是大模型主流，但仍是“顺序状态机”的重要参照系。

RNN 把“上一时刻的隐藏状态”直接传给下一时刻，这让它天然具备时间感。但因为梯度会在长链路上衰减， 纯 RNN 很难稳定记住很远的信息。LSTM 的门控机制，本质上就是在问：哪些状态该留，哪些该忘。

遗忘门
决定保留多少旧状态 把历史信息中不重要的部分衰减掉，避免状态污染。
输入门
决定写入哪些新信息 不是每个新 token 都值得强行写入长期记忆。
输出门
决定当前暴露哪些状态 让内部记忆和外部输出不必完全一致。
f_t = σ(W_f[h_{t-1}, x_t] + b_f) C_t = f_t ⊙ C_{t-1} + i_t ⊙ C̃_t h_t = o_t ⊙ tanh(C_t)

4. State Space / Mamba：它们重新回答了“长序列一定要靠全注意力吗”。

状态空间模型把序列看作一个连续动态系统，重点不在“我能看所有 token”，而在“我怎样把历史压缩成足够有用的状态”。 Mamba 这类模型的吸引力在于，它试图保留长上下文建模能力，同时降低注意力在超长序列下的二次复杂度。

  • 优势是长序列效率、流式处理和更平滑的延迟曲线。
  • 挑战是生态远不如 Transformer 成熟，工具链和社区经验还在积累。
  • 如果场景是日志、事件、信号流、极长文档，这类结构值得持续关注。

5. Diffusion 与 MoE：一个解决“如何生成更稳”，一个解决“如何把容量做大”。

Diffusion

扩散模型通过“逐步加噪、逐步去噪”学习数据分布，稳定性高，图像、视频、音频生成中表现强。 它不是一次性吐出结果，而是多步迭代逼近样本。

MoE

混合专家模型并不让所有参数每次都参与计算，而是让路由器选择少数专家激活。 好处是把参数容量做大，同时维持相对可控的每 token 计算量。

看论文时真正该盯住什么

  • 模型复杂度如何随上下文长度增长。
  • 训练稳定性是否依赖大量技巧。
  • 指标提升来自架构本身，还是更多数据和更大算力。
  • 推理延迟、吞吐、显存曲线是否给出。
  • 是否有明确的失败边界，而不是只展示最佳样例。

常见误区

  • 把“参数更多”误当作“结构更先进”。
  • 只看 benchmark，不看训练成本和推理成本。
  • 把学术最优结构直接搬进生产系统。
  • 忽略数据质量、路由策略、缓存和 serving 对实际效果的影响。
Frameworks

不要问“哪个框架最好”，要问“你当前处在哪个生命周期阶段”。

同样叫“AI 框架”，训练框架、模型库、推理引擎、应用编排层解决的不是一类问题。 如果不先分清层级，就会把 PyTorch、Transformers、LangChain、vLLM 混成一类，最后团队内部也无法形成一致判断。

训练层

定义模型、跑反向传播、做实验和大规模训练。关键词是 PyTorch、TensorFlow、JAX/Flax。

模型接口层

统一加载预训练模型、Tokenizer、Trainer、PEFT、量化器。关键词是 Transformers。

推理与应用层

真正决定部署体验、延迟与吞吐。关键词是 vLLM、ONNX Runtime、TensorRT、LangGraph。

1. PyTorch：研究与工程之间最平衡的默认起点。

如果团队没有强历史包袱，PyTorch 往往是最稳的训练起点。它的动态图、调试体验和生态完整度， 让“写模型、查梯度、跑实验、接外部库”几乎都不会遇到非常别扭的地方。

  • 优点：API 直觉化、社区最活跃、论文复现资源最多。
  • 风险：如果团队没有清晰的实验规范，代码会很快从 notebook 式原型膨胀成难维护工程。
  • 最适合：研究团队、模型团队、需要快速试错的应用组。

2. TensorFlow / Keras：不是“老”，而是更偏生产体系和稳定交付。

TensorFlow 的价值不只在训练本身，更在于它围绕部署、可视化、序列化、移动端和服务化形成的完整体系。 如果团队非常重视成熟生产链路，Keras + TensorFlow 仍然合理。

  • 适合已经有完整 TF 资产、需要稳定 serving 与跨端部署的团队。
  • Keras 降低了上手成本，但复杂自定义训练范式仍然会让开发体验逊于 PyTorch。

3. JAX / Flax：当你在追求极致训练效率、函数式变换和大规模并行。

JAX 的真正魅力在于“把数值程序当作可变换对象”。自动并行、自动微分、vmap、pmap、jit 让它在大规模训练里非常有吸引力， 但它对团队工程素养要求也更高。

  • 适合：基础模型团队、追求极致训练吞吐的研究型组织。
  • 不适合：希望快速搭建普通应用团队，或者只做轻量微调的产品组。

4. Transformers / vLLM / LangGraph：这是三层，不要混着选。

工具 定位 你为什么需要它
Transformers 模型库与训练接口 快速加载开源模型、Tokenizer、Trainer、PEFT、量化组件
vLLM 高吞吐推理引擎 优化批处理、KV cache 和大模型 serving，真正决定线上吞吐
LangChain / LangGraph 应用编排层 组织工具调用、状态机、多步任务，不是用来替代底层模型训练或 serving

框架选择矩阵

目标 首选
快速原型 / 论文复现 PyTorch + Transformers
超大规模训练 JAX/Flax 或 PyTorch 分布式
成熟部署链路 TensorFlow 或 PyTorch + ONNX/TensorRT
高吞吐开源模型服务 vLLM
Agent / 工具编排 LangGraph

团队最常见的错误拆法

  • 产品团队直接把“LangChain”当成整个 AI 技术栈。
  • 模型团队只讨论训练，不提前把 serving 成本纳入评估。
  • 工程团队把推理框架问题错当成模型架构问题。
  • 组织层面没有把“训练、推理、编排、评估”分开负责。

落地建议

  • 如果你做公开站点内容产品：先把稳定数据流、推理链路、缓存与风控做好，再谈更复杂模型。
  • 如果你做内部知识应用：Transformers + 检索层 + 轻量编排通常比一开始上复杂 Agent 更稳。
  • 如果你做模型训练：先确认评测体系和可重复实验规范，否则框架选型意义不大。
真正的工程判断不是“我会不会背这些名词”，而是能否回答四个问题： 这个模型为什么适合这个任务、它最贵的成本在哪里、什么时候该换结构、什么时候该换框架而不是换模型。
